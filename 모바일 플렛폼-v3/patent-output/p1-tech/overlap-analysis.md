# FireNavi 선행기술 중복성 검토

작성일: 2026-06-02  
목적: 선행기술과의 중복 여부 판단  
결론: **중복 없음 - 모든 기술요소 특허출원 가능**

---

## 질문: 선행기술 조사 결과가 내 아이디어와 비교하여 중복된 게 있니 없니?

### 답변: **중복 없음**

FireNavi의 5대 핵심 기술은 선행기술과 **개념·방법·구조·목적**에서 모두 차별화되어 있으며, 단순 개선이 아닌 **근본적으로 다른 접근 방식**을 사용합니다.

---

## 1. 음향 이벤트 온톨로지 기반 자동 재난 트리거

### 선행기술 (Google Nest, Amazon Alexa)
- 고정 센서 또는 스마트홈 장치 음향 감지
- 단순 알림 전송 (푸시 메시지)
- 서버 푸시 의존

### FireNavi
- **스마트폰 마이크** 로컬 감지 (모바일 중심)
- **온톨로지 노드 매핑** (FireAlarmSound → 화재 대피 모드, ExplosionSound → 폭발 회피 모드)
- **네트워크 장애 시에도 로컬 자동 활성화** (0.3초)

### 중복성 판단: ❌ 중복 없음
- **구조 차이**: 고정 센서 vs 스마트폰 마이크
- **처리 방식**: 단순 알림 vs 온톨로지 의미 매핑
- **독립성**: 서버 의존 vs 로컬 자동 작동

---

## 2. 센서·인간보고 온톨로지 정규화 기반 동적 화재맵

### 선행기술 (IBM Crowdsourced, 중국 Mobile Sensor)
- IBM: 텍스트 보고만 수집
- 중국: 센서값만 사용
- 단일 위험지도

### FireNavi
- **센서 데이터 + 자연어 보고 통합**
- **온톨로지 정규화** (SmokeOdor, ExitBlocked, LowVisibility)
- **베이지안 융합** (다수 보고 신뢰도 평가)
- **4채널 화재맵** (화재·연기·군중·출구 장애 분리)

### 중복성 판단: ❌ 중복 없음
- **입력 통합**: 텍스트 OR 센서 → 텍스트 AND 센서
- **정규화 방법**: 개별 처리 → 온톨로지 의미 노드 통합
- **출력 구조**: 단일 맵 → 4채널 독립 맵

---

## 3. 공간 온톨로지 기반 인프라프리 실내 다층 측위

### 선행기술 (Apple Indoor, Google Maps)
- WiFi + IMU 좌표 추정
- 출력: (x, y, floor)
- 일반 내비게이션 용도

### FireNavi
- WiFi + IMU + 기압계 + 자력계
- **공간 온톨로지 매핑** (x,y,floor → "4층 동쪽 복도" → 계단 A 연결 → 연기 위험)
- **대피 의사결정 직접 연동**

### 중복성 판단: ❌ 중복 없음
- **출력 형식**: 좌표 → 대피 의미 공간
- **활용 목적**: 일반 길찾기 → 재난 대피 의사결정
- **추가 정보**: 없음 → 층·복도·계단·출구·피난구역 의미

---

## 4. 취약계층 제약 온톨로지 기반 안전 마진 자동 적용

### 선행기술 (일본 Wheelchair Evacuation)
- 수동 프로필 설정
- 단순 경로 필터링 (계단 제외)
- 보호자 연동 없음

### FireNavi
- **취약계층 온톨로지** (이동능력·감각·의료·보호자 관계)
- **안전 마진 계수 (α) 자동 산출**
- **보호자 동기화 경로 자동 생성**
- **구조 우선순위 자동 산정**

### 중복성 판단: ❌ 중복 없음
- **자동화**: 수동 설정 → 온톨로지 기반 자동 판단
- **안전 마진**: 개념 없음 → α 계수 자동 적용
- **보호자 연동**: 없음 → 동기화 경로 자동 생성

## 5. 온톨로지 공유 기반 삼중 AI 엔진 동기 아키텍처

### 선행기술 (MIT ML Evacuation)
- 단일 강화학습 모델
- 독립 작동
- 설명 가능성 없음

### FireNavi
- **삼중 엔진** (Prediction·Behavior·Decision)
- **온톨로지 공유 동기화** (공통 의미체계)
- **출력값 온톨로지 노드 변환** (FireSpreadZone, Bottleneck)
- **설명 가능한 추천 사유 생성**

### 중복성 판단: ❌ 중복 없음
- **AI 구조**: 단일 모델 → 삼중 엔진
- **동기화**: 독립 → 온톨로지 공유
- **설명 가능성**: 없음 → 자연어 사유 생성

### 핵심 차별점 3가지

1. **온톨로지 기반 의미 체계**  
   → 선행기술은 데이터를 수치로 처리, FireNavi는 의미 노드로 변환

2. **자동화 수준**  
   → 선행기술은 수동 설정 또는 단순 알림, FireNavi는 로컬 자동 활성화 + 개인별 맞춤

3. **설명 가능성**  
   → 선행기술은 블랙박스 AI, FireNavi는 추천 사유 자연어 생성

## 특허심사관 예상 질문 & 답변

**Q1**: "Google Nest도 화재경보음을 감지하는데, 이것과 뭐가 다른가?"  
**A**: Google Nest는 고정 센서로 감지하여 단순 알림만 전송합니다. FireNavi는 **스마트폰 마이크로 로컬 감지**하고, 음향을 **온톨로지 노드로 매핑**하여 **대피 모드를 자동 활성화**합니다. 네트워크 장애 시에도 작동하며, 개인별 대피 경로까지 연동됩니다.

**Q2**: "Apple도 WiFi로 실내 위치를 추정하는데?"  
**A**: Apple은 좌표(x, y, floor)만 제공합니다. FireNavi는 좌표를 **"4층 동쪽 복도" 같은 대피 의미 공간**으로 변환하고, **계단 A 연결 → 연기 위험 판단 → 대체경로 추천**까지 연동됩니다. 단순 측위가 아닌 **재난 대피 의사결정 시스템**입니다.

**Q3**: "IBM도 크라우드소싱으로 재난 정보를 수집하는데?"  
**A**: IBM은 텍스트 보고만 수집합니다. FireNavi는 **센서 데이터 + 자연어 보고를 온톨로지로 통합**하고, **베이지안 융합으로 신뢰도를 평가**하며, **4채널 독립 화재맵**(화재·연기·군중·출구)을 생성합니다. 데이터 수집이 아닌 **의미 기반 위험지도 생성 시스템**입니다.
