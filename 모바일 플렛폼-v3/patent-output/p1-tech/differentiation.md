# FireNavi 차별성 근거

작성일: 2026-06-02  
목적: 중복된 것이 없는 이유와 근거 제시  
결론: **온톨로지 기반 의미 체계 + 설명 가능한 AI가 핵심 차별점**

---

## 핵심 질문: 중복된 것이 없는 이유와 근거가 뭐니?

---

## 근거 1: 패러다임의 차이 - 데이터 처리 vs 의미 이해

### 선행기술의 접근 방식
- **데이터 중심**: 센서값, 좌표, 수치를 그대로 처리
- **처리 방식**: 임계값, 통계, 머신러닝 예측
- **출력**: 수치, 좌표, 확률값

### FireNavi의 접근 방식
- **의미 중심**: 데이터를 온톨로지 노드로 변환
- **처리 방식**: 지식그래프 관계 추론
- **출력**: 설명 가능한 추천 사유

### 구체적 예시

| 상황 | 선행기술 | FireNavi |
|------|---------|----------|
| 음향 감지 | "85dB 소음 감지" | "**FireAlarmSound** 온톨로지 노드 → 화재 대피 모드" |
| 위치 추정 | "(120, 45, 4층)" | "**4층 동쪽 복도** → 계단 A 연결 → 연기 위험 높음" |
| 사용자 보고 | "연기 냄새" (텍스트) | "**SmokeOdor** 온톨로지 노드 → 화재맵 갱신" |
| 사용자 유형 | "휠체어 사용자" (프로필) | "**WheelchairUser** → cannotUse(Stair) → α = ∞" |
| 경로 추천 | "경로 A: 120m" | "경로 A는 **연기 위험**이 높아 제외, 경로 B 추천" |

### 왜 이것이 중복이 아닌가?

**철학적 차이**: 선행기술은 "무엇이 감지되었나"를 처리하고, FireNavi는 "**그것이 무엇을 의미하는가**"를 추론합니다.

## 근거 2: 통합 vs 분리

### 선행기술의 한계
- 음향 감지 시스템 (독립)
- 실내 측위 시스템 (독립)
- 크라우드소싱 시스템 (독립)
- 경로 추천 시스템 (독립)
- **→ 각각 독립적으로 작동, 상호 연결 없음**

### FireNavi의 통합 구조
```
음향 감지 → 온톨로지 노드 → 화재맵 갱신
        ↓                    ↓
    위치 추정 → 공간 노드 → 경로 계산
        ↓                    ↓
  사용자 상태 → 제약 노드 → 안전 마진
        ↓                    ↓
  센서 데이터 → 위험 노드 → 삼중 엔진
                              ↓
                    개인별 대피 경로 + 추천 사유
```

### 구체적 연결 예시

**시나리오**: 시각장애인이 4층 동쪽 복도에서 화재경보음을 듣는 상황

| 단계 | 선행기술 (분리) | FireNavi (통합) |
|------|----------------|-----------------|
| 1. 음향 감지 | "화재경보음 감지" → 푸시 알림 전송 | "FireAlarmSound 노드" → 대피 모드 자동 활성화 |
| 2. 위치 추정 | "(120, 45, 4층)" 좌표만 | "4층 동쪽 복도" → 계단 A, 계단 B 연결 |
| 3. 사용자 유형 | 프로필 확인 (별도 시스템) | "VisuallyImpaired" 온톨로지 노드 |
| 4. 위험 분석 | 화재 감지 (별도 시스템) | "계단 A → 연기 위험 높음" (화재맵 연동) |
| 5. 경로 계산 | 최단거리 계산 | 계단 A 제외 + 음성 안내 + 단순 경로 우선 |
| 6. 안내 방식 | 화면 표시 | **음성 안내**: "왼쪽으로 10m 이동 후 계단 B로 대피하세요" |
| 7. 추천 이유 | 없음 | "계단 A는 연기 위험이 높고, 시각장애인에게 음성 안내가 제공됩니다" |

### 왜 이것이 중복이 아닌가?

**통합 수준**: 선행기술은 각 기능이 독립, FireNavi는 **온톨로지 지식그래프가 모든 정보를 연결**합니다.

## 근거 3: 설명 가능성 (Explainability)

### 선행기술의 한계
- "경로 A를 추천합니다" (끝)
- 왜 그 경로인지 설명 없음
- 블랙박스 AI

### FireNavi의 설명 가능성
```
추천 경로: 경로 B (4층 복도 → 계단 B → 3층 → 출구 5)

추천 이유:
1. 사용자는 **시각장애인**으로 분류되어 음성 안내가 제공됩니다.
2. 계단 A는 **연기 위험**이 높아 제외되었습니다.
3. 계단 B는 현재 혼잡도가 낮고 **음성 안내**에 적합합니다.
4. 경로 B는 복잡도가 낮아 **시각장애인**에게 안전합니다.
```

### 온톨로지 기반 추론 과정

```mermaid
User → type: VisuallyImpaired
VisuallyImpaired → needsGuidanceChannel: Voice
VisuallyImpaired → preferRouteComplexity: Low

Corridor_4E → connectedTo: Stair_A
Corridor_4E → connectedTo: Stair_B
Stair_A → hasHazard: SmokeHigh
Stair_B → hasHazard: SmokeNone

Route_A → passesThrough: Stair_A
Route_A → penalized: SmokeHigh
Route_A → excluded

Route_B → passesThrough: Stair_B
Route_B → routeComplexity: Low
Route_B → recommended

Decision → recommends: Route_B
Decision → reason: "연기 회피 + 음성 안내 적합 + 복잡도 낮음"
```

### 왜 이것이 중복이 아닌가?

**설명 구조**: 선행기술은 결과만 제공, FireNavi는 **온톨로지 관계 기반 추론 과정을 자연어로 생성**합니다.

## 근거 4: 자동화 수준

### 선행기술의 한계
- 사용자가 앱 실행 (수동)
- 프로필 수동 설정
- 서버 푸시 의존
- 경로 재탐색 시 지연

### FireNavi의 자동화
| 단계 | 선행기술 | FireNavi |
|------|---------|----------|
| 재난 감지 | 서버 푸시 대기 | **로컬 음향 감지 0.3초** |
| 대피 모드 | 사용자 앱 실행 | **자동 활성화** |
| 위치 추정 | GPS 없으면 불가 | **WiFi + IMU + 기압계 자동** |
| 사용자 유형 | 수동 입력 | **온톨로지 자동 추론** |
| 안전 마진 | 수동 설정 | **α 계수 자동 산출** |
| 경로 전환 | 재탐색 요청 | **위험도 임계값 초과 시 자동 전환** |
| 보호자 연동 | 수동 연락 | **동기화 경로 자동 생성** |

### 왜 이것이 중복이 아닌가?

**자동화 철학**: 선행기술은 "도구"(사용자가 사용), FireNavi는 **"보조 에이전트"**(시스템이 판단하고 실행)입니다.

---

## 근거 5: 온톨로지 지식그래프의 근본적 차이

### 선행기술 - 데이터베이스 구조
```sql
User(id, name, type)
Location(x, y, floor)
Route(start, end, distance)
Hazard(type, severity)
```
→ 테이블 간 관계는 외래키로만 연결

### FireNavi - 온톨로지 지식그래프
```turtle
Person:User_001 rdf:type WheelchairUser
WheelchairUser owl:subClassOf VulnerablePerson
WheelchairUser rdfs:constraint cannotUse(Stair)

Location:Corridor_4E schema:connectedTo Location:Stair_A
Location:Stair_A hazard:has Fire:Zone_03
Fire:Zone_03 hazard:type SmokeHigh

Route:A route:passesThrough Location:Stair_A
Route:A rdfs:inferredProperty excluded
```
→ 관계가 의미를 가지며, **추론 가능**

### 추론 예시

**질의**: "User_001에게 적합한 경로는?"

**선행기술 (SQL 쿼리)**:
```sql
SELECT * FROM Route WHERE distance < 100;
```
→ 단순 조건 검색

**FireNavi (온톨로지 추론)**:
```sparql
SELECT ?route WHERE {
  ?user rdf:type WheelchairUser .
  WheelchairUser rdfs:constraint ?constraint .
  ?route route:passesThrough ?location .
  ?location schema:type ?type .
  FILTER NOT EXISTS {
    ?constraint apply(?type)
  }
  ?route hazard:riskScore ?score .
  FILTER (?score < 0.3)
}
ORDER BY ?score
```
→ **의미 기반 제약 추론** + 안전 마진 자동 적용

### 왜 이것이 중복이 아닌가?

**지식 표현**: 선행기술은 데이터 저장, FireNavi는 **의미와 규칙을 포함한 지식 구조**입니다.

## 근거 6: 실제 작동 증거 - BTS 콘서트 유즈케이스

### 시나리오
BTS 콘서트 종료 후 3번 게이트 주변 화재 + 압사 위험 발생

### 선행기술 방식 (가정)
1. 서버가 화재 감지 → 푸시 알림 전송
2. 모든 관객에게 "3번 게이트 피하세요" 동일 메시지
3. 관객이 앱 열고 지도 확인
4. 최단 경로 검색
5. 혼잡 발생 시 재검색

### FireNavi 방식 (실제)
```
1. 화재경보음 감지 (0.3초)
   → FireAlarmSound 노드 → 대피 모드 자동 활성화

2. 관객 1 (일반 성인, 1층 A구역)
   → 위치: "1층 A구역" → 2번 출구 안내
   → 이유: "3번 게이트 화재, 2번 출구 혼잡도 낮음"

3. 관객 2 (휠체어 사용자, 1층 B구역)
   → 위치: "1층 B구역" → 4번 출구 (경사로 있음)
   → 이유: "휠체어 사용자, 계단 제외, 경사로 우선"

4. 관객 3 (외국인, 2층 C구역)
   → 위치: "2층 C구역" → 5번 출구
   → 안내: 영어 "Exit via Gate 5, smoke detected at Gate 3"

5. 관객 4 (어린이 + 보호자, 1층 D구역)
   → 보호자 동기화 경로 자동 생성
   → 이유: "어린이와 보호자가 같은 출구로 대피"

6. 실시간 갱신
   → 2번 출구 혼잡도 증가 → 자동으로 6번 출구로 재배정
```

### 왜 이것이 중복이 아닌가?

**개인화 수준**: 선행기술은 "모두에게 동일", FireNavi는 **4,000명에게 4,000개의 서로 다른 경로** (온톨로지 기반 개인별 제약 자동 적용)

## 근거 7: 법적·기술적 근거

### 신규성 (Novelty) 충족 근거
1. **온톨로지 기반 의미 체계**: 선행기술에 없음
2. **삼중 엔진 동기화**: 선행기술은 단일 모델 또는 독립 작동
3. **설명 가능한 추천 사유 생성**: 선행기술은 블랙박스
4. **로컬 자동 활성화**: 선행기술은 서버 푸시 의존
5. **4채널 독립 화재맵**: 선행기술은 단일 맵

### 진보성 (Inventiveness) 충족 근거
1. **자동화 수준 비약적 향상**: 수동 → 완전 자동
2. **통합 수준 비약적 향상**: 분리 → 온톨로지 통합
3. **설명 가능성 비약적 향상**: 블랙박스 → 자연어 사유
4. **개인화 수준 비약적 향상**: 동일 안내 → 개인별 맞춤
5. **신뢰성 비약적 향상**: 네트워크 의존 → 로컬 독립 작동

### 산업성 (Industrial Applicability) 충족 근거
1. **공연장**: BTS 콘서트 6만 관객 실시간 개인별 안내
2. **병원**: 환자 이동능력 자동 판단 + 의료진 우선순위
3. **학교**: 어린이 보호자 동기화 + 다국어 안내
4. **호텔**: 외국인 관광객 다국어 안내
5. **공항**: 대규모 군중 분산 + 취약계층 우선 구조
