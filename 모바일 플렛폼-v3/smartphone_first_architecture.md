## 1. 5단계 파이프라인 (Five-Stage Pipeline)

```
[Stage 1]  음향 트리거 (Acoustic Trigger)
              ↓ SOLAS 표준 화재경보음 감지
[Stage 2]  분산 측위 (Distributed Localization)
              ↓ WiFi RSSI + IMU + 집단 보정
[Stage 3]  대화형 마이크로 설문 (Conversational Survey)
              ↓ 3문항 × 3초 응답
[Stage 4]  폰 센서 자동 수집 (Passive Sensor Fusion)
              ↓ 마이크/IMU/조도/기압/카메라
[Stage 5]  크라우드소싱 화재맵 + 개인별 경로
              (Crowdsourced Risk Map → Personalized Routing)
```

## 2. Stage 1 — 음향 트리거 (Acoustic Trigger)

### 2.1 작동 원리

SOLAS 화재경보음은 국제 표준으로 고정되어 있습니다:
- **General Emergency Alarm**: 7회 short blast + 1회 long blast
- **주파수 범위**: 500~1000 Hz
- **음압**: 75 dB 이상 (전 객실 가청)

스마트폰 마이크 + 경량 음향 분류 모델(~50KB)이 이 패턴을 99% 정확도로 감지합니다.

### 2.2 기술 스택

| 항목 | 기술 |
|------|------|
| iOS | AVAudioEngine + Core ML (Sound Classification) |
| Android | AudioRecord + TensorFlow Lite (YAMNet/PANNs 경량화) |
| Web (PoC) | Web Audio API + AnalyserNode (FFT 기반 패턴 매칭) |
| 모델 크기 | ~50KB (MobileNetV2 기반 음향 임베딩) |
| 추론 시간 | <50ms |
| 정확도 | 99.2% (Sound classification benchmark) |
| 배터리 소모 | 시간당 1~2% (Apple/Google 저전력 음향 감지 활용) |

### 2.3 작동 시나리오

```
[T+0초]    선내 화재 발생 → 자동 화재경보 발령
[T+0.5초]  4,000개 폰 마이크가 동시에 패턴 감지
[T+1초]    각 폰 앱이 background → foreground 자동 활성화
[T+1.5초]  WebSocket 연결 시작, 위치/센서 정보 송신
[T+3초]    전체 4,000개 폰 활성화 완료
```

### 2.4 거짓 알람 방지

- **공간 일치 검증**: 같은 구역의 10대 이상이 동시 감지해야 트리거 확정
- **음원 분류**: 단순 사이렌 vs SOLAS 패턴 구분
- **확률적 검증**: 0.5초 윈도우 내 패턴 반복 확인
- **선사 관제센터 ACK**: 자동 활성화 + 수동 확인 이중화

### 2.5 선례 (이미 작동하는 기술)

| 사례 | 활용 |
|------|------|
| Apple Sound Recognition (iOS 14+) | 화재경보·사이렌·도어벨 감지 |
| Google Live Caption / Sound Notifications | 알람·사이렌 감지 |
| Shazam | 음향 핑거프린팅 |
| Music ID 시스템 | 사전 등록 패턴 매칭 |

✅ **기술적 검증 완료, 신규 발명 아닌 응용**

## 3. Stage 2 — 분산 측위 (Distributed Localization)

### 3.1 다중 신호원 융합

| 신호원 | 정확도 | 비고 |
|--------|--------|------|
| 기존 선내 WiFi RSSI 핑거프린팅 | 5~10m | 선박에 이미 설치된 AP 활용 |
| 폰 IMU(가속도+자이로) Dead Reckoning | 30초 내 ±2m 누적 | 단기 정확 |
| 기압계 (Barometer) | 층 ±1층 | iPhone 6+ 이후 내장 |
| 자력계 (Magnetometer) | 방향 ±5° | 경로 안내용 |
| BLE 비콘 (있으면) | 3~5m | 옵션, 선택적 |
| **집단 근접 그래프** | ★ 1~3m | 4,000명 상호 거리 추정으로 보정 |

### 3.2 집단 보정 알고리즘 (Crowd Calibration)

```
1. 각 폰의 1차 위치 추정값 P_i ± σ_i
2. 폰 간 BLE/WiFi-Direct로 상호 신호 강도 측정
3. 그래프 최적화 (Graph SLAM)로 전체 위치 동시 보정
4. 정박 시 알려진 랜드마크(엘리베이터·로비)와 매칭
5. 최종 정확도: 2~5m (개별) → 1~3m (집단)
```

### 3.3 기존 v2.0 디바이스 대비

| 항목 | v2.0 Priority Device | v3.0 Smartphone |
|------|---------------------|------------------|
| 정확도 | 2~3m | 2~5m (개별) / 1~3m (집단 보정 후) |
| 하드웨어 비용 | $24K/척 | $0 |
| 분실 리스크 | 매 항차 보충 | 승객 본인 폰 |
| 충전 책임 | 선사 | 승객 본인 |
| 다국적 승객 처리 | 언어 라벨 필요 | OS 내장 번역 |
| 비상시 배터리 | 별도 충전소 5개소 | 본인 폰 + 보조배터리 보편화 |

→ **정확도 약간 감소, 그러나 운영 부담 100% 제거**

### 3.4 핵심: GPS 없이도 작동

GPS는 실내·지하에서 작동하지 않습니다. v3.0은 GPS에 의존하지 않으며, 모든 측위가 **선내 인프라(기존 WiFi) + 폰 자체 센서**로 완결됩니다.

## 4. Stage 3 — 대화형 마이크로 설문 (Conversational Micro-Survey)

### 4.1 설문 구조

화재 인지 후 5초 이내에 푸시 알림으로 전달:

```
🚨 FireNavi 긴급 — 5층 객실 R504 인근으로 추정

Q1. 🔥 불꽃이 보이나요?
   [예 / 아니오 / 모름]

Q2. 💨 연기 보이나요 / 냄새 나나요?
   [냄새만 / 보임 / 없음]

Q3. 👥 주변 사람들 상태?
   [평온 / 달림 / 패닉]

→ 응답 시 즉시 개인별 경로 표시
```

### 4.2 응답 옵션

| 응답 방식 | 적합 상황 |
|----------|----------|
| 터치 버튼 (기본) | 일반 상황 |
| 음성 응답 (Whisper API) | 시야 차단, 달리는 중 |
| 비명/소음 자동 분석 | 무응답 시 마이크로 자동 추정 |
| 가속도 분석 | 무응답 시 IMU로 달림/넘어짐 자동 분류 |

### 4.3 다국어 대응

| 항목 | 처리 |
|------|------|
| 메시지 언어 | 폰 OS 언어 자동 매칭 (12개국어) |
| 음성 응답 | Whisper/Google STT 다국어 |
| 답변 정규화 | LLM 기반 의미 매핑 |

### 4.4 응답률 현실적 추정

| 시간대 | 응답률 | 비고 |
|--------|--------|------|
| T+5~15초 | 30~40% | 즉시 응답자 |
| T+15~30초 | 60~70% | 누적 응답률 |
| 미응답자 | 30~40% | 폰 센서로 간접 추정 |

→ **4,000명 × 70% = 2,800개 명시적 보고 + 1,200개 센서 추정 = 4,000개 전체 추정값 확보**

### 4.5 v2.0과의 차이

v2.0은 IoT 센서 500대 = 500개 데이터 포인트.
v3.0은 4,000명 × 3문항 × 5초 = **명시적 12,000 + 폰센서 4,000×7종 = 28,000+ 데이터 포인트.**

**데이터 밀도 56배 증가, 비용 0원.**

## 5. Stage 4 — 폰 센서 자동 수집 (Passive Sensor Fusion)

### 5.1 활용 센서 매트릭스

| 센서 | 데이터 | 화재 대응 활용 |
|------|--------|---------------|
| 🎙️ 마이크 | 음압 레벨, 비명, 군중 소음 | 패닉 자동 감지 |
| 📡 가속도 | 보행/달림/정지/넘어짐 | 부상자 자동 식별 |
| 🌀 자이로 | 자세 변화 | 쓰러짐 감지 |
| 💡 조도 | 환경 밝기 | 정전/연기 농도 추정 |
| 🌡️ 기압 | 고도 변화 | 층 이동 자동 감지 |
| 🧭 자력계 | 방위각 | 경로 안내 |
| 📷 카메라 (사용자가 들면) | 영상 | CV 연기·불꽃 자동 분석 |
| 📍 GPS (실외 시) | 위치 | 갑판·구명보트 위치 |
| 🔋 배터리 | 잔량 | 알람 표시용 |
| 🔥 온도 센서 (일부 기종) | 온도 | 직접 화재 근접 감지 |

### 5.2 무응답자 자동 추정 알고리즘

```
입력: 폰 IMU + 마이크 + 조도 (사용자 응답 없음)
출력: 추정된 상황 라벨

규칙 예시:
- 가속도 std > 2.0 m/s² + 마이크 > 80dB → "달림+패닉"
- 가속도 ≈ 0 + 자이로 ≈ 0 (10초 이상) → "정지/의식불명 가능성"
- 기압 급변 → "계단 이동"
- 조도 급감 → "연기 또는 정전"
- 마이크 비명 패턴 → "주변 위험 임박"
```

### 5.3 학습 데이터 확보 전략

| 단계 | 데이터 |
|------|--------|
| Phase 1 | 화재훈련 시 자원자 폰 데이터 수집 |
| Phase 2 | 다양한 시설 일상 데이터로 베이스라인 |
| Phase 3 | 실제 화재 사례 분석 (사후) |
| Phase 4 | 합성 데이터 + 시뮬레이션 보강 |

## 6. Stage 5 — 크라우드소싱 화재맵 + 개인별 경로

### 6.1 베이지안 융합

```
각 격자 (x, y, z)에 대해:
  P(화재 | 보고들) = P(보고들 | 화재) × P(화재) / P(보고들)

가중치:
  - 명시적 시각 보고: 가중치 1.0
  - 명시적 냄새 보고: 가중치 0.7
  - 센서 자동 추정: 가중치 0.4
  - 음성 톤 분석: 가중치 0.3

업데이트 주기: 5초
공간 해상도: 2m × 2m 격자
시간 해상도: 5초 윈도우
```

### 6.2 화재맵 vs 기존 시스템

| 항목 | 기존 IoT 센서 | v3.0 크라우드소싱 |
|------|-------------|------------------|
| 데이터 포인트 | 500 | 4,000 + 자동추정 |
| 시각 확인 | 불가 | 4,000명의 눈 |
| 냄새 감지 | 불가 | 4,000명의 코 |
| 거짓 알람 판별 | 약함 | 다수 교차 검증 |
| 인접 객실 화재 조기 감지 | 센서 트리거 후 | **30~120초 앞서 감지** |

### 6.3 개인별 경로 계산

| 입력 | 처리 |
|------|------|
| 베이지안 화재맵 | A* Dynamic + Risk Penalty |
| 개인 위치/이동능력 | 6유형 분류 (기존 v2.0 유지) |
| 출구별 혼잡도 | 동적 분산 (CrowdPenalty) |
| 폰 IMU 진행방향 | 자력계 기반 화살표 안내 |
| 출력 | 푸시 + 음성 + 진동 |

### 6.4 적응 루프 (Adaptive Loop)

```
승객 이동 → IMU/위치 갱신 → 신규 보고 → 화재맵 재학습
                                    ↓
                            다른 승객 경로 보정
                                    ↓
                            푸시 알림 전송
```

**전체 갱신 주기: 5~10초**, 개인별 경로 갱신: **즉시 (변경 발생 시)**

## 7. 시스템 아키텍처

### 7.1 전체 흐름

```
[Passenger Smartphones × 4,000]
   ├─ Audio Listener (Stage 1)
   ├─ Position Estimator (Stage 2)
   ├─ Survey UI (Stage 3)
   ├─ Sensor Logger (Stage 4)
   └─ Route Renderer
        ↕ WebSocket / MQTT
[Ship Edge Server]
   ├─ Position Aggregator
   ├─ Bayesian Fusion Engine
   ├─ A* Dynamic Router
   ├─ Crowd Balancer
   └─ Push Notification Service
        ↕
[Cloud Backup / Multi-Ship Learning]
```

### 7.2 통신 부하 계산

| 항목 | 값 |
|------|----|
| 폰당 송신 주기 | 5초 |
| 폰당 페이로드 | ~500 bytes (위치 + 센서 + 응답) |
| 4,000대 동시 대역폭 | 4,000 × 500B / 5s = **400 KB/s** |
| 기존 선내 WiFi 대역폭 | 1~10 Gbps |
| **부하율** | **< 0.1%** |

✅ **기존 인프라로 완전 처리 가능**

### 7.3 장애 대응

| 시나리오 | 대응 |
|---------|------|
| WiFi 다운 | BLE Mesh Peer-to-Peer 폴백 (폰 간 직접) |
| Edge 서버 다운 | 클라우드 백업 / 폰 캐시 경로 30초 지속 |
| 개별 폰 다운 | 주변 폰들이 그 위치 인근 정보로 보완 |
| 인터넷 단절 | 선내 Edge 단독 작동 (외부 의존 X) |

## 8. 핵심 차별화 (USP)

### 8.1 USP-1 · 하드웨어 제로 (Zero-Hardware)
- 선사·시설 운영자가 새로 설치할 디바이스 0개
- 기존 WiFi 인프라만으로 작동
- **설치비 95% 절감, 드라이독 0일**

### 8.2 USP-2 · 인간 = 센서 (Human-as-Sensor)
- 4,000명의 눈·코·판단력이 가장 강력한 화재 감지기
- 기계 센서가 트리거하기 *전*에 인접 객실 승객이 이미 보고
- **30~120초 조기 감지 가능**

### 8.3 USP-3 · 자가 진화 (Self-Evolving)
- 매 항차마다 실제 패턴 학습
- 화재 훈련 데이터 자동 축적
- 후발 진입자가 따라잡기 어려운 데이터 해자

### 8.4 USP-4 · SaaS 즉시 배포 (Instant SaaS)
- 앱 업데이트만으로 즉시 도입
- 1척 도입 후 다음 척 즉시 가능
- B2B Capex → SaaS 모델 전환

### 8.5 USP-5 · 보편 적용 (Universal)
- 크루즈 외 모든 공간 즉시 적용
- 빌딩·호텔·병원·학교·지하철·경기장
- 단일 코드베이스로 모든 도메인 커버

## 9. v2.0 자산의 v3.0 활용

기존 v2.0 자료가 폐기되는 것이 아니라, **상위 계층**으로 재배치됩니다.

| v2.0 자산 | v3.0 활용 |
|-----------|----------|
| 3개 AI 엔진 알고리즘 | Stage 5 화재맵·경로계산 엔진의 핵심 |
| 9개 수학 모델 | 베이지안 융합, A* Dynamic, Risk Map 구현 |
